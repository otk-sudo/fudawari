# 札割りプランナー（fudawari）実装計画

要件は `docs/requirements.md`、画面の最終形は `docs/design/mock/` を正とする。この計画は、要件を実装可能なタスクに分け、担当・依存関係・受入条件・未決事項の期限を示す。計画ができたことは製品の完成を意味しない。

## 0. 進め方

### 0.1 担当

| 担当 | 役割 |
|---|---|
| tdd-test-engineer | 受入条件をテストにして、失敗すること（Red）を確かめる。テストの設計と不足の分析 |
| frontend-react-developer | テストを通す実装（Green）と、その後の整理（Refactor）。React／TypeScript／画面 |
| quality-reviewer | 差分を独立して読み取りレビューする。修正はしない（指摘は実装担当へ戻す） |
| 親（Claude Code 本体） | DB・インフラ・CI・外部サービスの設定、担当への依頼と結果の統合、Git 操作、ユーザーへの確認 |

- 実装とレビューを同じ担当に兼ねさせない。
- 同じファイルを複数の担当が同時に編集しない。並行して進める場合は、変更対象のファイルが重ならないタスクだけにする。
- Supabase・Cloudflare・GitHub の設定など、ユーザーのアカウントで操作する作業や費用・公開を伴う作業は、ユーザーの明示的な許可を得てから行う。

### 0.2 1 タスクの流れ（TDD）

1. **親**：作業ブランチを用意し、担当にタスク ID・変更してよい範囲・受入条件・関連する未決事項を渡す。未決事項が残っていれば、先にユーザーへ確認する。
2. **tdd-test-engineer**：受入条件をテストにする（単体は Vitest、画面の操作は Testing Library または Playwright）。テストを実行し、**期待どおりの理由で失敗する**ことを確かめて記録する。
3. **frontend-react-developer**（DB・CI のタスクは親）：テストを通す最小の実装をし、テストが通ったら整理する。テストの期待値は変えない。テストが誤っている・仕様と食い違うと判断したら、理由を添えて親に戻す。
4. **quality-reviewer**：差分を読み取りでレビューする（不具合、安全性、性能、型、テストの十分さ、モック・要件との食い違い）。指摘は 3 の担当が直し、必要なら再レビューする。
5. **親**：CI が通り、受入条件をすべて満たしたことを確かめてから統合する（PR・マージはユーザーの許可の範囲で行う）。この計画の状態欄を更新する。

設定だけのタスク（雛形、CI など）は TDD の対象外とし、「コマンドが成功する」「わざと失敗させると CI が赤くなる」などで確かめる。

v1 の締め切りまでの運用（`docs/plan-v1.md` 5 章）：複数のタスクを 1 つの PR にまとめ、レビューは PR 単位で 1 回にする（PR の中ではタスクごとにコミットを分ける）。再レビューは原則 1 回まで。指摘は「ブロッカー」と「ブロッカーでない」に分け、後者は v1.1 送り一覧に入れる。

### 0.3 完了の条件（全タスク共通）

- 受入条件をすべて満たし、その証跡（実行したテストとコマンドの結果）がある。
- 型チェック・Lint・単体テスト・画面テストが通る。
- quality-reviewer の指摘に対応済み（対応しない指摘は理由を記録）。
- 要件やモックと異なる判断をした場合、`docs/requirements.md` を更新した（未決事項を決めた場合は「13. 未決事項」も更新）。

### 0.4 状態の表し方

未着手／進行中／レビュー中／完了／ブロッカー（理由を書く）。現時点ではすべて未着手。

## 1. 最初の着手：「初期フォルダ構成」を先にすることを推奨

**推奨：初期フォルダ構成（Next.js・Playwright・GitHub Actions の設定込み。T1-1）を先に行う。テーブル設計（T3-2）は、ドメインの型（T1-2）ができた後に、親がフェーズ 2 と並行して文書として進める。**

理由：

1. **TDD の前提になる。** テストの仕組み（Vitest・Playwright）と CI がないと、以降のどのタスクでもテスト → 実装 → レビューの順で進められない。全担当の作業の土台になる。
2. **価値の中心は DB なしで作れる。** 取り込み・割り振り・一覧・画像で保存・差分は、静的 JSON とブラウザ内の保存だけで完結する（要件 5 章）。モックの 2026夏イベのデータをテスト用の定義（fixture）にすれば、Supabase なしで最後まで作れる。
3. **一般の画面との契約は「公開定義 JSON」で、テーブルではない。** 一般の画面が読むのは公開版の JSON なので、先に JSON の形をドメインの型として固め（T1-2）、テーブルはそれを保存・生成する側として後から設計する方が手戻りが少ない。
4. **テーブル設計は未決事項の影響を多く受ける。** 公開の反映方式（U7）、札とゲーム内の札の値の対応（U10）、特効の対象の範囲（U11）、札の操作の詳細（U16）、「最新」「開催中」の扱い（U18）が決まっていない。また Supabase は作り始める前に無料プランの最新の条件を確かめる必要がある（U2）。
5. **マイグレーションも CI から適用する計画になっている**（要件 8 章）。リポジトリと CI が先にある方が自然。
6. 補足：Supabase の無料プランは約 7 日アクセスがないと停止するため、使い始めるのは管理者向けの機能を作る直前でよい。

着手前に決めること：U6（この推奨でよいか）と U19（Next.js の出力方式）。U19 は雛形の設定に直接影響する。

## 3. タスク

各タスクの書き方：担当（テスト → 実装 → レビュー）、依存、変更対象（予定）、受入条件、関連する未決事項。

### フェーズ 0：着手前の確認

#### P0 本書と要件の確認、着手前の未決事項の決定
- 担当：親（ユーザーに確認する）
- 依存：なし
- 受入条件
  - ユーザーが `docs/requirements.md` と本書を確認した。
  - U6（最初の着手）と U19（Next.js の出力方式・招待リンクの URL の形）が決まり、`docs/requirements.md` の未決事項の表が更新されている。
  - U1（艦船マスタ）の調査を始めている（T1-5 の前に決まっていればよい）。

### フェーズ 1：土台

#### T1-1 初期フォルダ構成
T1-1a〜T1-1d に分ける。設定作業のため TDD の対象外。T1-1a〜c の差分は quality-reviewer がレビューする。

**T1-1a Next.js の雛形**
- 担当：実装 frontend-react-developer → レビュー quality-reviewer
- 依存：P0
- 変更対象（予定）：`package.json`、`tsconfig.json`、`next.config.*`、ESLint の設定、`src/app/`、`src/styles/`、`CLAUDE.md`（予定の記述を実際の内容に更新）
- 受入条件
  - Next.js（App Router）＋ TypeScript（strict）で、型チェック・Lint・ビルドのコマンドがローカルで成功する。
  - U19 で決めた出力方式でビルドし、ローカルで配信するとトップ画面が開く。
  - UI ライブラリの既製のテーマ、雛形のサンプル画面、使わない依存が入っていない。
  - CSS 変数でダーク／ライトの色を切り替えられる土台がある（色の値はモック基準）。
  - パッケージマネージャーと Node のバージョンを決め、`CLAUDE.md` のコマンドを実際のものに直した。

**T1-1b テストの仕組み**
- 担当：tdd-test-engineer → レビュー quality-reviewer
- 依存：T1-1a
- 変更対象（予定）：Vitest・Testing Library・Playwright の設定、`e2e/`、スモークテスト
- 受入条件
  - Vitest ＋ Testing Library で、部品を描画するスモークテストが通る。
  - Playwright で、トップ画面を開いて見出しを確かめるテストが通る。
  - どちらも、期待値をわざと変えると失敗することを確かめた記録がある。
  - 単体テストと画面テストのコマンドが `package.json` にある。

**T1-1c GitHub Actions**
- 担当：親 → レビュー quality-reviewer
- 依存：T1-1b
- 変更対象（予定）：`.github/workflows/`
- 受入条件
  - PR ごとに型チェック（tsc）・Lint（ESLint）・単体テスト（Vitest）・画面テスト（Playwright）が動く。
  - 確認用の PR で、わざと失敗するテストを入れるとチェックが失敗する。

**T1-1d Cloudflare Pages との連携**
- 担当：親（ユーザーのアカウントでの操作と許可が必要）
- 依存：T1-1a
- 受入条件
  - PR ごとにプレビュー URL が作られ、main へのマージで本番がビルド・デプロイされる。
  - Playwright は CI の中でビルドした静的出力に対して実行する（D1。2026-10-16 承認）。本番ブランチは main（D2）。

#### T1-2 ドメインの型、公開定義 JSON の形、テスト用の定義データ
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-1b
- 変更対象（予定）：`src/domain/`（型・検証）、テスト用の定義データ（2026夏イベの E1〜E3。モックの札・段階・大事さ・特効）
- 受入条件
  - 要件 4.1・4.3 の概念（イベント・海域・段階・札・大事さ・特効・艦の個体・割り当て）を型で表している。
  - 公開定義 JSON を読み込んで検証する関数がある。テスト用の定義データは検証を通り、不正な例（存在しない札を参照する段階、数値でない倍率、重複した ID など）は理由つきのエラーになる。
  - 画面・保存の仕組み・通信に依存しない。
  - 実行時の検証にライブラリを使う場合は、依存の追加を親に相談してから入れる。
- 関連する未決事項：U10（札にゲーム内の札の値を持たせるか）、U11（特効の対象の範囲）

#### T1-3 特効の計算
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-2
- 変更対象（予定）：`src/domain/` の特効計算
- 受入条件（単体テスト）
  - 個体 × 段階の倍率を求められる（艦名は改装段階を問わず一致する）。
  - 札ごとのスコア Σ（倍率 − 1）× 100 × 重み（普通 1・重要 2・難所 3）を求められる。テスト用データで「初霜改二を連合艦隊に置くと +81」になる。
  - 個体ごとに、効く札をスコアの高い順に並べ、効かない札の一覧も返せる。
  - 札の中で特効があるか、最大の倍率はいくつかを返せる（一覧のバッジ、画像の「特効」の印に使う）。
  - 段階ごとに、その札に割り当てた艦のうち特効がある隻数を返せる（一覧の「特効 n 隻」に使う）。
  - 1 隻が同じ段階で複数のグループに当てはまるときは、倍率を掛け合わせる（U12）。
  - v1 では艦種補正を扱わない（U11。このため U5 の掛け合わせの問題は起きない）。

#### T1-4 共通レイアウト（左メニュー、ヘッダー、テーマ、ウィンドウの土台）
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-1b
- 変更対象（予定）：`src/components/`（左メニュー、ヘッダー、ウィンドウ）、`src/app/` のレイアウト、`src/styles/`
- 受入条件
  - 左メニューの項目が、権限（一般／協力者／管理者）ごとに要件 2.2 どおりになる（権限の値はこの時点では仮の入力。T3-4 で実際のログイン状態につなぐ）。
  - 左上の「札」でホームへ移動する。
  - 「設定」でウィンドウ（Radix UI）が開き、開いている間は後ろの画面を操作できない。×・「閉じる」・背景のクリックで閉じる。
  - 画面モード（ダーク／ライト／端末に合わせる）を切り替えると、CSS 変数で色が変わる。
  - モックの「見え方の確認」は作らない。
- 関連する未決事項：U4（アプリ名。文字列を 1 か所にまとめておけば後で変えられる）

#### T1-5 艦船マスタ
- 担当：親（入手元の調査、利用条件の確認、ユーザーへの確認）→ tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：U1 の決定
- 変更対象（予定）：マスタデータの置き場所、`src/domain/` のマスタ参照
- 受入条件
  - 入手元と利用条件が `docs/requirements.md` に記録され、ユーザーが了承している。
  - 艦 ID から、艦名・改装段階を問わない艦名・艦種・艦型・改造状態（未改造／中間改造／最終改造）・図鑑 ID（と、運の表示に必要な値）を引ける。単体テストがある。
  - 知らない艦 ID は「名前が分からない艦」として扱える。
  - 新しい艦が実装されたときのマスタ更新の手順が文書になっている。
  - ゲームの画像を含めない。

### フェーズ 2：一般利用者の機能（Supabase 不要）

#### T2-1 取り込みデータの解析
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-2、T1-5
- 変更対象（予定）：`src/domain/` の取り込み解析
- 受入条件（単体テスト）
  - 制空権シミュ形式のサンプルから個体の一覧を作れる。サンプルは仕様から作るか、ユーザーから提供を受ける（実際の個人データをリポジトリに入れる場合はユーザーに確認する）。
  - 「ロック済みだけ」「Lv 下限」で絞り込める。
  - 名前が分からない艦の数と、札が付いている艦の数を返す。
  - 空の入力、壊れた JSON、想定外の形でも例外で止まらず、理由を返す。
  - 解析は通信を行わない純粋な関数である。
- 関連する未決事項：U8（形式の正確な仕様）、U9（個体の同一性）

#### T2-2 ブラウザ内の保存（Dexie）
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-2、T2-1
- 変更対象（予定）：`src/lib/` の保存処理
- 受入条件
  - 個体、取り込みの情報（日時・条件）、割り当て、設定を保存し、再読み込み後に元に戻る。
  - 再取り込みしても、同じ個体の割り当てが残る（U9 の決定に従う）。
  - 「取り込んだ艦娘データを削除」で個体は消え、割り当ては残る。
  - 定義が変わって存在しなくなった札の割り当ての扱いがテストされている（U17 の決定に従う）。
  - 保存の形を変えるためのバージョン移行の仕組みと、そのテストがある。
  - テストで IndexedDB の代わりが必要な場合は、依存の追加を親に相談してから入れる。
- 関連する未決事項：U9、U17

#### T2-3 公開定義の読み込み
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-2
- 変更対象（予定）：定義の読み込み処理、テスト用の定義データを静的 JSON として置く場所（予定：`public/data/`）
- 受入条件
  - 静的 JSON（当面はテスト用の定義データ）を読み、検証してから使う。
  - 読み込みや検証に失敗したら、画面に理由を表示する。
  - 各画面のヘッダーに最新イベント名を表示できる。過去のイベントを選ぶ欄は作らない。

#### T2-4 取り込み画面
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-4、T2-1、T2-2
- 受入条件
  - 要件 3.4 の表示・文言・操作がある。

  - Playwright：貼り付け → 取り込む → 隻数が表示される。
  - Playwright：取り込みの操作中に、貼り付けた内容を含む通信が発生しない。

#### T2-5 割り振り：状態と操作
- 担当：tdd-test-engineer → frontend-react-developer → quality-reviewer
- 依存：T1-3、T2-2

- 受入条件（単体テスト）

  - 「ここに置く」「（札名）に置く」でその札へ移り、選択が外れる。
  - 札の列へ落とすと移動、別の艦に重ねると入れ替え（相手が控えなら自分が控えへ）、控えへ落とすと割り当てが外れる、自分に落としても変わらない。
  - ドラッグを始めると選択が外れる。
  - 「元に戻す」で直前の変更が戻る（範囲は U22 の決定に従う）。
  - 割り当ての変更が保存される。

- フェーズ 2 の間、権限やイベント定義はテスト用の値を使う。フェーズ 3 で実際の値につなぐ際は、フェーズ 2 のテストが引き続き通ることを確かめる。
- 依存ライブラリは要件 6 章に挙げたものを基本とする。それ以外を追加する場合は、理由を添えて親に相談する。
- 要件・モックと違う実装をしたくなった場合は、実装する前に親へ戻す。親が必要に応じてユーザーに確認し、`docs/requirements.md` を更新する。
