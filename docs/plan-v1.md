## 2. v1 の完成の定義

| 区分 | v1 完成の条件 |
|---|---|
| 機能 | モックの全画面（ホーム、一覧、割り振り、取り込み、差分、設定、画像で保存、ログイン、協力者と招待〔招待を受ける側を含む〕、イベント定義、同時編集、編集中の表示、保存の記録、公開）が要件どおりに動く。6.4 で既定にした動きも含む。チェックポイントで切った機能は「v1.1 送り一覧」に記録し、ユーザーが了承している |

| テスト | 各 PR の受入条件のテストが通り、PR 本文に Red（失敗した理由）と Green の記録がある。Playwright：取り込み、割り振り（移動・入れ替え）、画像で保存、定義（割り込み・削除・衝突確認）、権限ごとのメニューと操作の可否。DB：RLS・RPC の可否のテスト |
| CI | PR ごとに、型・Lint・単体・画面・DB のテストが緑。release への取り込みで、本番 DB にマイグレーションが適用される（D2 の変更により main ではなく release） |

| デプロイ先 | Cloudflare Pages に main の最新版がデプロイされている。Supabase 本番にマイグレーションが適用されている。本番 URL で Discord ログイン、招待、定義の公開から一般画面への反映までが通る |
| 文書 | requirements.md の未決事項の表、運用手順書（T4-3）、v1.1 送り一覧 |

**本番公開の扱い**
- 段階 1「v1 実装完了」は、上の表の「デプロイ先」以外がそろった状態。段階 2「v1 本番稼働」は、ユーザーの許可を得て本番に反映し、本番 URL で確認できた状態。**この計画の目標は段階 2（日 09:30）**。許可が出なければ、段階 1 で締め切りを迎える。
- Cloudflare の本番ブランチを main にする場合（D2）、マージがそのまま本番 URL への反映になる。告知（URL を X などで広めること）は v1 の完成とは別で、ユーザーが判断する（この計画の範囲外）。
- U1 が決まらない場合は段階 1 までとし、本番公開は U1 が決まってから行う。

## 4. 並行の流れ（レーン）とファイルの持ち分

| B 一般・画面 | 同上 | PR-01（雛形）, 03, 05, 06, 07 | `src/components/`、`src/app/` のレイアウトと各画面のルートの入れ物、`src/styles/`、`src/lib/definition/`（定義の読み込み）、`src/features/{home,assign,list,export-image}/` |

- 各 PR は親が作る作業ブランチで進める。同じフォルダでは別々のブランチを同時に開けないので、レーンごとに別の git ワークツリーを使う（ワークツリーごとに npm install が要る）。
- 依存は、PR-01 で要件 6 章のもの（＋Supabase のクライアント、IndexedDB のテスト用の代替）をまとめて入れる。以後、`package.json` を変えるのは親だけ。
- 各画面の `src/app/<画面>/page.tsx` は、PR-03 で全画面分の空の入れ物を作る。以後は、その画面の機能を持つレーンが編集する。
- 共有の型（`src/domain/` の定義・個体・割り当て）は A の持ち分。C が変えたいときは親に戻し、親が A の作業との順番を決める。
- 権限は、PR-03 で B が `src/features/auth/` に 1 つの入口（仮の値）を作り、画面はそこから受け取る作りにする。PR-03 のマージ後は `src/features/auth/` を A の持ち分とし、PR-10 で A が中身だけを差し替える（レイアウトには触らない）。設定ウィンドウも同じ考え方で、枠は B、中身は A が作る。
- PR-12 が定義画面に差し込むのは 2 か所（「保存の記録を見る」と「編集中」の表示）。差し込み口は C が用意し、A はそこに部品を渡すだけにする。
- 前の PR がマージされる前に次の PR を始めるときは、前の PR のブランチから分ける（積み上げ）。前の PR がマージされたら、main を取り込む（rebase・force push はしない）。

**時間内に収める工夫（TDD とレビューは省かない）**
- レビューは PR 単位で 1 回にする（PR の中ではタスクごとにコミットを分ける）。再レビューは原則 1 回まで。指摘は「ブロッカー」と「ブロッカーでない」に分け、後者は v1.1 送り一覧に入れて先に進む。
- 先回りする：実装担当が今の PR を作っている間に、tdd-test-engineer は別のワークツリーで次の PR のテスト（Red）を書く。
- テストの優先順位：① `src/domain/` の純粋な関数（計算・解析・差分・定義の編集・マージ）を Vitest で厚く確かめる、② 画面の主な操作を Testing Library で確かめる、③ Playwright は要件 9 章の 5 つの流れと権限に絞る、④ 見た目はレビューでモックと見比べ、画像を比べるテストは作らない。
- 共通のテスト用データ（2026夏イベの定義、600 隻の個体）は PR-02 で作り、全レーンで使う。
- PR 本文に、Red の証跡（コマンドと失敗した理由）と Green の結果を残す。後から書いたテストを TDD 済みとは書かない。
- CI の Playwright は Chromium だけで動かし、ブラウザはキャッシュする（D1）。
- 親が担当に依頼するときは、「変更してよいファイル」「受入条件」「決まった U の内容」を必ず書く。
