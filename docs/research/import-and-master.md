# 調査結果：U8（取り込み形式）・U9（個体の同一性）・U1（艦船マスタ）

調査日時：2026-10-16 20:40〜21:00 頃（親）

## U8 制空権シミュ形式（事実：noro6/kc-web の src/classes/convert.ts `Convert.readShipStockJson` を読んで要約）
受け付ける入力は2種類。
1. `svdata=` で始まる文字列：接頭辞を除いて JSON 解析し、`api_data.api_ship` 配列を使う（ゲームの API 応答そのもの）
   - 主なキー：`api_id`（個体ID）、`api_ship_id`（艦のマスタID）、`api_lv`、`api_exp[0]`、`api_kyouka[0..6]`（近代化改修：火力・雷装・対空・装甲・運・耐久・対潜）、`api_slot_ex`、`api_sally_area`（出撃札）、`api_sp_effect_items[].api_kind`、`api_onslot_max`/`api_slotnum`、`api_locked`（ロック）
2. 短縮形式の JSON 配列：`id`（個体ID。`ship_id` がある新版の場合）、`ship_id`（マスタID）、`lv`、`exp[0]`、`st[0..6]`（近代化改修。並びは api_kyouka と同じ）、`ex`、`area`（出撃札）、`sp[]`、`slots`
   - 旧版は `ship_id` がなく `id` がマスタID（個体IDなし）
- ロック情報は `svdata=` 形式にしかない。短縮形式では「ロック済みだけ」が効かない
- マスタIDが 0／欠損の要素は飛ばす。Lv 下限未満は除外。Lv 0 は 1 に補正
- 出撃札は値をそのまま持つ（解釈しない。偽の値は 0）
- 運の表示値は「マスタの運の初期値 ＋ 近代化改修の運（st[4]／api_kyouka[4]）」で求める必要がある（推測：特殊効果アイテムは運に影響しない）
- kc-web にはライセンスの表示がない（README にも記載なし）。コードやデータは流用しない。形式の仕様として参考にするだけ

## U9 個体の同一性（事実＋提案）
- 新しい短縮形式と svdata 形式には個体ID（`id`／`api_id`）がある → 再取り込みしても個体IDで同じ個体と判定できる
- 個体IDがない旧形式は連番になるため同一性を保てない → 【提案】旧形式は「割り当ては引き継げない」と表示する

## U1 艦船マスタの入手元（事実＋提案）
- 候補A：Tibowl/api_start2（GitHub）。ゲームの api_start2（マスタデータ）を定期的に保存しているリポジトリ。最終更新 2026-10-14（「Update 2026-10-14」）。ライセンスの表示なし
- 候補B：kcwikizh/kcdata（GitHub Pages）。ship／shipclass／shiptype などに分かれたデータ。ライセンスの表示なし
- いずれもゲーム会社のデータを第三者が公開しているもので、明示的な利用許諾はない（他の艦これツールも同じ立場で利用している）
- api_start2 の api_mst_ship にある主な項目：api_id、api_sortno（図鑑番号）、api_name、api_stype（艦種）、api_ctype（艦型の番号）、api_luck（運の初期値・最大）、api_aftershipid／api_afterlv（改造先）
  - 艦型の名前（「白露型」など）は api_start2 にない（番号だけ）→ 自前の対応表が必要
  - 「改装段階を問わない艦名」「改造状態（未改造／中間／最終）」は改造の連鎖から自前で求める
- 【提案】ビルド時に候補Aの start2.json を取得し、必要な項目だけを抜き出した最小のマスタ（自前の形式）を生成して静的ファイルとして配る。画像は含めない。艦型名は自前の対応表。利用の可否（ライセンス表示がないデータを使うこと）はユーザーが判断する
- 代案：管理者が自分のゲームクライアントの api_start2 を貼り付けてマスタを更新する（第三者のリポジトリに依存しない。定義画面に入力欄が増える。モックにはない）
- 2026-10-16 21:00：ユーザーが候補A（Tibowl/api_start2）を承認

## start2.json の実物で確認したこと（2026-10-16 20:56 取得、3.2MB）
- 取得元：https://raw.githubusercontent.com/Tibowl/api_start2/master/start2.json
- トップ：`api_mst_*` のキーが直接並ぶ（`api_data` の包みはない）。`api_mst_ship`（1,755件。味方艦は api_id < 1500 で 866件）、`api_mst_stype`、`api_mst_shipupgrade` など
- 味方艦の主なキー：`api_id`、`api_sortno`（図鑑番号）、`api_sort_id`、`api_name`、`api_yomi`（読み。名前順の並べ替えに使える）、`api_stype`、`api_ctype`、`api_luck`（[初期値, 最大値]）、`api_aftershipid`（文字列。"0" は改造先なし）、`api_afterlv`
- 例：時雨 43 → 時雨改 243 → 時雨改二 145 → 時雨改三 961（961 の aftershipid は "0"）。いずれも api_ctype 23、api_yomi「しぐれ」
- `api_mst_stype`：1 海防艦、2 駆逐艦、3 軽巡洋艦、4 重雷装巡洋艦、5 重巡洋艦、6 航空巡洋艦、7 軽空母、8 戦艦、9 戦艦、10 航空戦艦、11 正規空母、12 超弩級戦艦、13 潜水艦、14 潜水空母、15 補給艦、16 水上機母艦、17 揚陸艦、18 装甲空母、19 工作艦、20 潜水母艦、21 練習巡洋艦、22 補給艦
- 艦型の名前のマスタはない（`api_ctype` は番号だけ、味方艦で 140 種類）→ 艦型名の対応表を自前で持つ。艦型名は「その艦型で最初の艦（図鑑順）の名前＋型」で多くは作れるが、例外は手で直す
- 改造の連鎖：`api_aftershipid` をたどる。未改造＝どの艦の改造先にもなっていない艦（改造先も改造元もない単独の艦も未改造）。最終改造＝改造先が "0" の艦と、**コンバート改装の輪に入っている艦すべて**（例：大鯨 → 龍鳳 → 龍鳳改 → 龍鳳改二戊 ⇄ 龍鳳改二 では、輪の 2 隻〔龍鳳改二戊・龍鳳改二〕が最終改造。2026-10-16 親が決定。PR-02 の実装どおり）。中間改造＝それ以外。改装段階を問わない艦名＝連鎖の起点の艦名（例：龍鳳改二戊 → 大鯨）

## 実データでの確認（2026-10-16 23:35、PR-04a で生成したマスタと start2.json で親が点検）
- 生成したマスタ：味方艦 866 隻。改造状態は 未改造 331・中間改造 175・最終改造 360
- コンバート改装の輪に入っている艦：53 隻（霞改二⇄霞改二乙、最上改二⇄最上改二特、加賀改二・改二戊・改二護、宗谷の 3 形態 など）。すべて最終改造になっている
- 「改造元が 2 つ以上ある艦」は 24 隻あるが、すべて輪の入口（例：最上改 → 最上改二 ← 最上改二特）。別々の起点から 1 隻に合流する形はない
- 艦型：140 種類。対応表（`src/domain/master/shipClassNames.ts`、107 件）にない 33 種類は「図鑑番号が最小の艦の起点の艦名＋型」で補う（海外艦は「〜級」にならないことがある。v1.1 で対応表を足す）。対応表の名前が所属艦の名前と結びつかない 26 種類（潜水艦の艦型・海外艦の級・大鷹型・丁型海防艦など）は、所属艦と照らして妥当なことを確認した
- 見本：時雨改三＝白露型・起点 時雨、雪風改二＝陽炎型、大井改二＝球磨型、龍鳳改二戊＝龍鳳型・起点 大鯨、鈴谷航改二＝最上型
